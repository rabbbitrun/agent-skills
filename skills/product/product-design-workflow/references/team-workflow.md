# 团队需求设计流程

适用于存量产品迭代与新增模块。本文件是这套工作流的流程规则来源，Skill 入口负责执行，模板负责承载记录。规则修改在此维护；项目提供明确约定或用户明确调整流程时，记录差异并遵循其要求，不把模板默认值当作额外审批要求。

## 路径选择

先确定用户本轮要什么，再根据改变的行为和影响范围选择路径。

| 路径 | 条件 | 最小流程与材料 |
| --- | --- | --- |
| 快速修改 | 文案、局部位置等；不改变业务规则、权限、数据或任务路径 | 变更说明 → 局部预览 → 验收；复用现有需求单，简单任务的对话或差异记录也可，无须新建完整 PRD |
| 常规需求 | 已有页面新增字段、筛选、入口或局部流程 | 精简 PRD → 受影响区域灰度原型 → 结构确认 → 必要细化 → 最终评审 |
| 完整设计 | 新模块、跨页流程或信息结构重组 | 需求澄清 → 精简 PRD → 灰度 HTML 线框原型 → 结构与流程确认 → 视觉及交互细化 → 最终评审 |

权限、计费、临床业务规则或数据写入发生变化时，即使只改一个控件，也至少补对应规则和验收项，不能按纯外观修改略过。局部业务变更可以走常规路径，不因此扩展整套产品设计。

已有决定仍适用时直接继续，不重新跑已完成阶段。若本轮只要 PRD、线框或影响评估，则只交付指定部分；后续阶段记录为未开始。

## 记录与职责

通常在项目既有需求目录下维护一个 `requirement.md`，路径优先遵循项目习惯。同等需求单或文档已存在时直接复用。仅在实际需要时添加灰度 HTML、细化原型或局部预览，不提前创建空文件。

- 需求负责人决定范围、业务规则及验收；设计负责人制作结构、交互和视觉；技术负责人核查实现约束。小团队可由同一人兼任，不强制增加评审人。
- AI 提出方案、维护记录并执行检查；未知负责人写“待指定”，不虚构姓名。当前请求者的明确确认可记为“当前用户”，保留可识别的消息或评审来源。
- 需求使用稳定编号，例如 `R-01`。验收项和原型说明引用同一编号。新增编号追加，删除项标记撤回，不重用已接受编号。
- 记录当前阶段、需求修订、现状基线、资产路径及版本、已确认范围、待决定项和下一步。资产未生成写“未生成”；源码、截图或批准记录只由用户描述时标明“用户提供，未读取核对”。
- 现状基线注明版本来源；无法确认线上对应提交时写“线上一致性未核实”。来源冲突只暂停受影响判断，保留其他可继续工作。

按材料是否已有基线决定记录形状：

- **新需求**：摘要与来源 → 需求及验收 → 待确认问题与下一步；资产、确认、变更和验证栏目随事件发生补充，不为填满模板逐项扩写。
- **已有基线的变更**：本次修订与范围 → 变更需求及对应验收 → 对资产和已有确认的影响 → 待决定问题与下一步。无影响编号引用原版本即可，保留原文及历史记录，无须在新增段落中再次描述它们。
- 同一事实保留一个正文位置，其他位置引用编号或来源。例如“原型未读取、未运行页面”集中记在来源与验证边界，不在摘要、每项需求、资产表及收尾反复声明。规则和验收能在同一行讲清楚时不再另写一遍；未知项只写入问题表并引用。

## 阶段契约

| 阶段 | 工作与最小交付物 | 完成条件 |
| --- | --- | --- |
| 需求澄清 | 用户与场景、现存问题、目标、范围、主要未知项 | 足以界定需求；影响结构或业务结果的未知项有明确问题与影响 |
| 精简 PRD | 必要的前置条件、输入与规则、结果、权限、失败路径、验收标准 | 每项需求能观察或判断对错；推测、建议和已知规则分开 |
| 灰度线框 | 复用现状，展示受影响结构、真实字段和代表内容、必要跳转及相关状态 | 能查看布局、走已实现路径；外部效果和未实现行为明确标注 |
| 结构与流程确认 | 提供可打开的具体版本、变化摘要及待决定问题 | 获得覆盖该版本与范围的明确确认；未确认部分仍待评审 |
| 视觉及交互细化 | 沿用项目组件和设计规范，补齐主次、反馈、校验及相关状态 | 与有效确认相符；新增结构问题回到受影响部分处理 |
| 最终评审 | 按需求编号检查覆盖情况、页面和交互；列通过项、问题、未验证项 | AI 检查完成后仍需人工验收；阻断问题关闭或有明确处置记录 |

未知规则不能因生成页面而变成已决定事实。先问影响目标、范围、规则和流程的问题；其他低风险、可逆选择可按现有惯例推进并说明。

线框原型中的显示、输入、开关及点击跳转不证明服务端业务正确。权限隔离、保存结果等真实行为需在实现阶段另验；设计验收与功能测试通过分别记录。流程终点是设计评审，生产开发、提交、发布或发消息给他人不由本技能默认授权。

## 确认与变更

常规和完整路径默认设置两个主要人工确认点：结构与流程确认、最终设计验收。快速修改不额外设置结构确认点，仍交付结果供验收。其他阶段按问题异步协作，无须逐步开会或逐段批准。

确认必须对应具体需求修订、资产版本和范围。记录确认人、日期、来源、结论及覆盖编号；不要猜日期、姓名或不存在的会议链接。可识别的当前消息也是来源，不必为了记录确认去联系其他人。

- “文件已生成”“AI 检查通过”、沉默或等待超时均不构成人工确认。
- 对刚呈现的明确方案说“按这个继续”，可确认该方案范围；含糊的“继续”在无对应评审对象时，不确认尚未展示的结构。
- 复用仍有效的确认；更换技能、开始新对话或进入下一阶段不会使它失效。资产与确认版本不一致时先查明差异，只复核有影响的部分。
- 用户明确调整或跳过默认阶段时，记录调整及其依据；记为“按用户要求跳过”，不伪造该阶段已评审通过。新任务的实现授权仍以用户请求为准。

发生变更时，在原记录中追加修订及影响：

1. 列出变更的需求编号、规则、页面、组件和依赖；结合代码或现有材料核对，不仅按文字相似度判断。
2. 保留原确认作为历史记录；标明受影响范围需要重审，无影响范围继续有效。
3. 仅暂停依赖变更决定的细化；先完成具体、可评审的局部方案，再请求对应确认。其他独立工作继续。
4. 对已实现的局部预览做对应验证，更新当前阶段、资产版本和下一步。

结构不变的视觉细化不自动撤销结构确认。字段语义、权限或流程改变则需要评估，即使改动被称为“小改一下”。

## 局部修改约定

使用本 Skill 修改已有页面或原型时默认生效，灰度与视觉细化阶段均适用，用户无需每轮再次声明。用户明确要求整体重设计时，以新的范围为准。

- 接受“页面／弹窗 + 元素名称或截图标记 + 怎么改”的简短反馈，例如“预约弹窗：医生放到日期前面”。沿用当前需求和已知页面上下文，不要求重复提交完整需求。
- 只调整用户指出的元素及明确指定的关系，其他布局、文案、样式和行为保持原样；不顺带美化、重构或重画整页。
- 确实需要连带修改时，先说明原因和影响范围，再做必要的最小调整。涉及尚未明确授权的业务含义、权限或流程变化时，先问清楚再执行相关动作；已有明确指示不重复确认。
- 先利用上下文和现有页面定位目标；仍存在多个同名元素，或“删除”无法区分隐藏入口与取消功能时，只问解决该歧义所需的一个简短问题。其他无歧义修改可继续。
- 回复只说“改了什么”和“还有什么待确认”。相关验证结果或未验证限制简短附在改动说明中；无待确认项就写无，不追加整份需求、无关建议或下一阶段方案。

## 工具与资产协作

- **存量页面**：先读页面索引，再定位相关源码、组件、样式和已知规则。有可用页面就做局部预览；整体框架作为上下文保留，未受影响部分不必灰度重画。设计授权只覆盖原型、草稿或已授权的实现改动。
- **新结构**：可用时使用 `wireframe`，仅加载当前阶段资源。结构已选定就做一个方向；存在实质分歧才比较不同方案。HTML 是此工作流的默认产出，用户指定其他格式时从其要求。
- **评审界面**：使用 Intent 时沿用其查看器和注释栏；已有 `requirement-review-wireframe` 工作台时沿用该工作台。不要相互嵌套。保留 `R-xx` 需求映射；若组件标记是逐页数字，在注释中写明对应需求编号，不擅改组件契约。
- **交互范围**：明确本轮是布局评审还是可点击流程。Intent 原型用于点击跳转，不承担条件逻辑或业务状态模拟；用静态状态页或说明呈现未实现分支。需要复杂行为验证时，另列验证任务，说明所需数据与环境。
- **视觉细化**：先用项目设计规范和组件，确有缺口再按需加载合适技能；灰度阶段不引入品牌探索、动效或额外方案。
- **依赖缺失**：说明缺少能力和影响。可交付同等范围时，用现有 HTML、原生控件与简单跳转替代，并标明未使用原技能；不自动安装技能、不把 Figma 请求悄悄改成 HTML。替代会改变用户指定交付物时，先确认替代选择，继续不受影响的需求整理。
- **只有截图**：用代表截图建立可复用页面基线，注明截图日期或版本（已知时）、推断与未确认行为。复用已有 HTML；无源码、接口或浏览器验证时如实标记，不将静态画面当作运行证据。

## 控制上下文与交付成本

首次只读需求摘要、进度和页面索引；按受影响编号展开源码及规则。模板只在建档时读取，阶段指南按需读取，不一次加载所有设计技能。

复用组件和既有原型，局部修改文件；对话只呈现变化及决定，不反复贴完整 PRD 或代码。截图用于现状核对和视觉验证，优先受影响区域。大批页面先完成核心流程或代表页面，再根据反馈扩展到用户请求的完整范围。

不承诺固定 token 节省比例。若要比较成本，应记录同类任务的实际用量、交付范围和返工次数。

## 最终检查与交接

逐项核对需求、原型和验收标准的映射；有浏览器能力时检查实际布局及已实现点击路径。检查结果采用“通过／失败／未验证／不适用”，分别写明方法和证据。文档核对不能替代浏览器测试或真实接口测试。

交接前确认：当前版本明确、未决问题有影响说明、确认记录可追溯、验收与验证结果未混淆。局部修改按“局部修改约定”反馈；其他任务简短报告本轮变化、验证情况、待确认项和一个下一步。

本标准由团队指定的维护负责人通过版本控制更新；未指定前不捏造角色。涉及路径或确认规则的修订先用真实需求试行，再同步 Skill 入口和模板中受影响的内容。
