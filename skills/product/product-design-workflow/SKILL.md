# 需求设计与评审

把需求推进到可评审、可交接的设计；复用已有产品和已确认决定。以 [团队流程](references/team-workflow.md) 为流程规则来源，不把每次修改都扩展成完整设计项目。

## 开始与恢复

1. 先定位现有需求记录、页面索引、源码或原型及确认记录。先读摘要，再读受影响部分；没有源码时可使用截图，但注明推断边界。
2. 读取团队流程的“路径选择”，用一句话说明本次路径、当前阶段和理由。新需求按需使用 [需求模板](assets/requirement-template.md)；已有同等记录则原位更新，不迁移格式、不另建一套文档。已有基线的变更按“记录与职责”写增量，避免重述整份需求。
3. 只执行本轮请求涵盖的阶段。仅请求方案、PRD 或线框时，做到该交付物即止；缺少决定时暂停依赖它的动作，继续独立工作。
4. 开始阶段前，按需读取团队流程中的阶段契约、确认与变更、工具协作。对已有页面或原型的修改默认执行[局部修改约定](references/team-workflow.md#局部修改约定)，用户无需逐轮重申。完成后更新同一份需求记录；局部修改按该约定简短反馈，其他任务报告改动、验证结果、待确认项和一个下一步。

## 按需使用资源

| 当前工作 | 使用方式 |
| --- | --- |
| 澄清、PRD、恢复进度 | 本技能及团队流程；只补当前阶段所需字段 |
| 新结构的灰度线框 | 可用时读取 `wireframe`；已有结构只做本次方向 |
| 存量页面局部修改 | 优先复用现有源码、组件或 HTML；设计任务不自动授权修改生产实现 |
| 视觉及交互细化 | 先查项目设计规范；确有需要时再加载适合的设计技能 |
| 独立需求标注工作台 | 可用时读取 `requirement-review-wireframe`；交付物只保留一套评审界面 |

依赖不可用时按团队流程说明可行替代，不自动安装或扩大任务。技能名称是能力路由，不依赖本机绝对路径。

## 使用示例

“按团队流程，给诊所列表增加服务版本筛选；默认全部，与其他条件组合，切换后回第一页。已有源码，本轮只要结构评审。”

选择常规路径 → 读取列表与筛选组件 → 在同一需求记录补规则和验收标准 → 复用页面做局部灰度预览 → 请用户确认受影响结构。已有导航和其他页面无需重画；没有接口时明确原型仅验证布局与跳转。

## 收尾

检查需求编号、资产版本、确认范围是否一致。文件生成、AI 检查、人工确认和运行验证分别记录；没有执行的检查标为未验证。确认及变更的判定统一遵循团队流程，不在此重复维护规则。
